### 왜 지금인가 (인과 사슬, 메인 세션 실측)

1. **ENH-388 (v2.1.33)** 이 Destructive Detector를 실제로 차단하도록 고쳤다
   (`scripts/unified-bash-pre.js:303-304`). 그전까지는 감사 로그에 `result:'blocked'`를
   쓰면서 명령을 통과시켰다. 수정 자체는 옳았으나, **잠복해 있던 규칙 정밀도 결함이
   실제 작업 중단으로 전환**되었다. 집행을 켜기 전 규칙 정밀도 검토가 없었다.
2. **이슈 #148**이 안전한 명령을 차단하는 3개 규칙을 통제군 포함 12케이스 재현
   하네스와 함께 신고했다. 메인 세션이 정확히 재현: **오탐 4건, 통제군 누락 0건**.
3. **16개 규칙 전수 감사** 결과 결함 범위는 신고의 약 **3배**였고, 같은 근본원인이
   **위음성**도 만들고 있었다.
4. 영향받는 규칙 대부분이 `critical/deny`다. 무인 실행에서 PreToolUse deny는 답할
   사람이 없어 **실패하지 않고 조용히 정지**한다 — 리포터는 한 스프린트에서 2회,
   매번 약 15분을 잃었고 유휴 감시 장치 덕에 겨우 발견했다.

코드베이스 자신이 그 비용을 이미 적어두었고, 리포터가 그대로 인용했다
(v2.1.34 주석, `destructive-detector.js`):

> "정확한 명령을 거부하고 따를 수 없는 조언을 주는 가드는 사람들이 꺼버리는 가드이며,
> 그러면 아무것도 보호하지 못한다."

### 수정 선례는 같은 파일에 이미 있었다 (G-001)

작업의 대부분은 **발명이 아니라 전파**다.

- **피연산자 경계**: `:289` — `text.match(/\b(?:rm|rimraf|Remove-Item)\b([^\n;|&]*)/i)`가
  다음 명령 구분자에서 피연산자 목록을 자른다. 주석에 이를 유발한 v2.1.34 사건이 기록돼 있다.
- **등급 부여**: `:54` — `severityFor: (text) => (deleteTargetIsBroad(text) ? 'critical' : 'high')`
- **액션 해석**: `resolveAction()` `:415-421` — `critical`은 항상 deny. 스스로 등급을
  낮춘 규칙만 `deny` → `ask`로 **정확히 한 단계** 완화하며, 침묵으로는 절대 가지 않는다.

## 6. 열린 질문 (해소 기록)

- **Q1 G-006 범위** → **포함 확정.** 같은 감사에서 측정된 오탐이며 `severity-grading`에 편입(ENH-445).
- **Q2 G-009/010/010b/011 등급** → **등급 미부여.** SQL 파괴 연산은 대상 범위가 위험도를 결정하지 않는다.
- **Q4 `resolveAction()`의 ask 계층 의미** → **실측으로 해소.** `resolveAction()`은 non-critical 등급에 대해 선언된 액션을 그대로 반환한다. `defaultAction`이 이미 `ask`인 5개 규칙(G-003/004/005/006/007)은 `severityFor`를 추가해도 **보고되는 심각도만 바뀌고 액션은 불변**이다. `ask` 아래 계층은 침묵뿐인데 `resolveAction()`이 설계상 거부한다. **따라서 등급 부여는 `deny` 계층 규칙에만 의미가 있고, ask 계층 오탐의 해법은 전부 경계 수정이다.** 이로써 ENH-443의 범위가 G-013 하나로 확정되고 G-004/G-007은 등급 대상에서 제외된다.
- **Q3 복구 경로 방향** → **Option B 채택** (메시지 정정 + 규칙 런타임 불변 유지 + ADR 0016).
